# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Danmaku (탄막 게임) — a 2D bullet-hell game built with **Unity 6000.3.23f1**, URP 2D renderer, the new Input System, and DOTween. Commit messages, code comments and docs are in Korean. `.editorconfig`: UTF-8, LF.

`CODEBASE_GUIDE.md` (Korean, per-class reference) is generated by Copilot via `.github/workflows/docs.yml` (push a `docs` tag) from whatever commit was tagged, so it can lag behind the code (its prompt still describes a removed `EnemyData` layer) — trust the source over it, and don't hand-edit it.

## Build / Run

- Running anything needs the Unity Editor (matching version). There are no lint or test commands and no tests (Unity Test Framework is installed but unused).
- Compile check without the Editor: `dotnet build Danmaku.slnx` (builds `Assembly-CSharp`, `Assembly-CSharp-Editor` and the `-firstpass` plugin projects). The `.slnx`/`.csproj` files are generated by the Editor, gitignored, point at the local Editor install and list every script explicitly — a newly added `.cs` file isn't compiled until Unity regenerates them.
- Build Settings scenes: `Assets/01.Scenes/Online/Title.unity` → `Online/LevelSelect.unity` → `Online/InGame.unity`. Title's Start button is a `UI/ButtonFinder` (`sceneName = "LevelSelect"`, loaded **additively** via `GameManager.LoadSceneAdditive`); `LevelSelector.Confirm` calls `GameManager.LoadInGameScene(level, player)`, which loads InGame and creates the "Runner" (`LevelRunner`) and "Player" (`PlayerController` + `PlayerAnimation`) objects at runtime. Every scene at the root of `01.Scenes/` is test-only.
- InGame has **no player and does not auto-start**: opening it directly in Play mode gives no player, and its scene `StageRunner` (`data = Datas/Stages/TestStage`, one phase, no boss) only runs from the `StageRunEditor` "시작" button. Play through Title → LevelSelect to get a player. `Datas/Levels/Normal` holds `Stages/Easy/E1_Stage` and `E2_Stage` (moved from `Esay`, folder names kept) (one phase each: about a minute of fairies, then a last boss with three spells; their bursts and spells are in `Bursts/Easy/` and `Spells/Easy/`, split into `Common`, `Stage1` and `Stage2`); the older `Stage1` (phase 1: only a mid-boss; phase 2: six fairies, then the last boss) is in no level; `Esay`/`Hard` have no stages. The level flow is unfinished (see Runtime flow). Keys: move WASD/arrows, slow Shift/Space/L, bomb X/K; the player auto-fires.
- Enter Play Mode Options has **domain reload disabled** (`ProjectSettings/EditorSettings.asset`), so static fields and static event subscriptions survive between play sessions — reset new static state explicitly (e.g. `[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]`).
- CI (`.github/workflows/build.yml`) builds **WebGL** (also the Editor's active platform) with `game-ci/unity-builder` when a `v*` tag is pushed (or on manual dispatch); the bot commits the output into `docs/` (GitHub Pages) with `[skip ci]`. Never hand-edit `docs/`.
- **DOTween Pro is a paid asset and is gitignored** (`Assets/Plugins/Demigiant/DOTweenPro*`, `DemiLib`; only free DOTween is tracked). It must exist locally (Title scene uses DOTween Pro animations; defines `DOTWEEN;DOTWEENPRO` are set); CI copies it from the private `PrivateStorage` repo. Never commit it.

## Architecture

Scripts live in `Assets/02.Scripts/`, compiled into `Assembly-CSharp` (no asmdefs; `Editor/` goes to `Assembly-CSharp-Editor`, `Assets/Plugins/` to the `-firstpass` assemblies). Asset folders are number-prefixed (`01.Scenes`, `02.Scripts`, `03.Textures`, `04.Materials`, `05.Prefabs`).

### Managers / singletons

- `Core/SingletonBehaviour<T>`: `Instance` finds an active `T` in the scene, and if there is none it **instantiates the first `T` prefab in `Resources/ManagerObjects/`** (with a warning). Use `ExistingInstance` in teardown code (`OnDisable`/`OnDestroy`) to avoid spawning one. Duplicates `Destroy` themselves in `Awake`, but the destroy is deferred, so subclasses overriding `Awake` must call `base.Awake()` and guard their own setup with `ExistingInstance == this`. `IsPersistent` enables `DontDestroyOnLoad` (`GameManager`, placed in both Title and InGame).
- InGame holds prefab instances of `UIManager` (which nests `Input Handler.prefab`: `InGameInputHandler` + `PlayerInput`), `GameManager`, `EnemyManager` and `BulletManager`; `StatusManager` isn't placed and spawns from `Resources` on first access.
- A UnityEvent serialized in a prefab can only target objects inside that prefab or other assets, so pointing it at another manager calls the **prefab asset**, not the live singleton. The result panel's Restart/Exit buttons call `GameManager.LoadScene` on `GameManager.prefab` (only its static/global effects work — hence `GameManager` also resets pause state on `sceneLoaded`), and `StatusManager.prefab`'s events have no target, so `UIManager.Awake` subscribes its setters in code. Wire cross-manager calls in code through `.Instance` (as `UI/ButtonFinder` does).

### Timing

All gameplay runs in `FixedUpdate` (Fixed Timestep = 1/60) and moves with `Time.fixedDeltaTime`. Durations in data and code are **fixed frames**: wait with `yield return new WaitForFixedFrame(n)` (`Core/`) or the cached `GameManager.WaitForFixedUpdate`; `GameManager.FrameToSecond`/`SecondToFrame` convert for DOTween. `GameManager.Pause()`/`Resume()` are ref-counted and set `Time.timeScale` (0 halts `FixedUpdate`, i.e. all gameplay); `LoadScene` and every scene load reset them.

### Danmaku data (ScriptableObjects in `Assets/Datas/`, menus under Level/Stage/Spell/Bullet/Player)

```
LevelData (Datas/Levels: Esay = [Stage1], Normal/Hard empty) → StageData[]
StageData → PhaseData[] → EnemyChain[] → EnemyPattern[]   (+ PhaseData.Boss: EnemyPattern, spawned after the chains)
  EnemyPattern (struct: type, name, color, score, Body: BulletData, AniCon, SpellCard[], spawn pos, item drop counts, first-burst wait)
    SpellCard (PresentHP, TimeLimit) → BurstData[] (PresentPosition, WaitForFrame) → BulletPattern[]
      BulletPattern = BulletData + InitialBullet (color/pos/vel/torque) + BulletSequenceBase + WaitForFrame
```

`PlayerData` (`Datas/Players`: Baekyeon, Yujin): Speed, SlowSpeed, InitialHP/InitialPower (hundredths, 0–500), `PlayerAttacks: BurstData[]` (indexed by power level 0–5, so it needs 6 entries), `PlayerSpell` (unused), `AniCon`. `LevelData.ScoreMultiplyer` is a `double` (Esay 0.8, Normal 1, Hard 1.3) but nothing reads it yet.

`SpellCard.TimeLimit` is an `int` in frames, counted from that spell's start (after its wait): `N > 0` repeats the burst chain until N frames pass, while `0` **or any negative value** ends the spell at its first check, so only the chain's bullets before its first wait fire (a one-spell enemy then dies and scores right away). There is no "never" value: for a spell that should last until the enemy is killed, use a huge limit (e.g. `2147483647`). A regular enemy's limit should end when its MoveOut burst has taken it off-screen, otherwise the repeated chain brings it back in. Most existing spells (31 of 35) still have `0`, and every `Bursts/Stage1/*` burst has `PresentPosition = (0, 0)` with `WaitForFrame > 0`, so Stage1 enemies fly to the screen centre — both are data still to be fixed.

Every enemy BulletData has `Tag = Enemy` except the unused `BulletDatas/Laser`, saved before `BulletData.Tag` existed (`Tag` `0` = no collision, see Bullets).

Items are BulletData tagged `Power`/`Score` (`Datas/Items`; sprites in `03.Textures/Items/`). When a spell is **killed** (not timed out), `Enemy.ItemFirework` drops `EnemyPattern.DropPowerCount` power items, then `DropScoreCount` score items, one per fixed frame at the enemy's position, through `BulletManager.SpawnPowerItem`/`SpawnScoreItem`. Those spawn the `PowerItemPattern`/`ScoreItemPattern` set on `BulletManager.prefab`, whose sequence `Sequences/RandomThenDown_18F` runs `RandomDirectionSequence` for 18 frames, then `DownwardSequence`. Still unfinished: no enemy data sets drop counts yet (all 0); both item patterns have zero `InitialVelocity`, so items never move; `ItemFirework` runs on the enemy, so a regular enemy, released right after its last spell, drops only the first item; and `PlayerController.InhaleItem` (pulls `Item` bullets within 3 units, collects them for +10 power whatever their type) is never called, so nothing collects items.

There is no separate enemy asset: enemies are defined inline in `EnemyPattern` inside `PhaseData`. An enemy's hit radius comes from its `Body` BulletData (`Distance`), and its sprite from `Body.BulletImage` unless `EnemyPattern.AniCon` is set: `EnemyManager.SpawnEnemy` assigns it to the prefab's Animator (null = no animation), and the clips then drive the sprite (without one, both prefabs show a plain white square). Only the `Stages/Easy` phases set it (`Animate/Enemy/Fairy/Fairy.controller` for fairies, `Boss/Boss.controller` for bosses).

Most data fields are `[field: SerializeField]` auto-properties, serialized as `<Name>k__BackingField` (`BulletDataEditor` and `DeadzoneGizmos` look them up by that string). Renaming such a property drops its saved values unless you add `FormerlySerializedAs("<OldName>k__BackingField")`.

### Runtime flow

- Level flow (WIP): `LevelRunner.Initialize(level)` sets a stage enumerator; `Start` creates its own "Runner" `StageRunner` and subscribes `StartLevel` (next stage → `Initialize` + `StartRun`) to `OnStageEnd`. `Start` also calls `StartLevel` once for the first stage. Still broken: `StageRunner` raises `onStageEnd` before clearing `isRunning`, so the chained `StartRun` for the next stage is ignored (and every stage end pauses and shows the result panel).
- `StageRunner` walks phases as a coroutine: it spawns each chain's patterns via `EnemyManager.SpawnEnemy` (pooled `05.Prefabs/EnemyPrefab` for `EnemyType.Common`, 10 pre-warmed in `EnemyManager.Start`; otherwise instantiates `BossPrefab` / `EnemyBoss`) without waiting for them to die, then, if `PhaseData.Boss.Type` isn't `Common`, spawns the boss and waits on `EnemyBoss.BossAlive()`. 300 frames after the last phase it pauses and shows the result panel (`UIManager.ResultBoardOn`), as game over does.
- `Enemy.StartPattern` runs each SpellCard in its `Run` coroutine: sets HP to `PresentHP` and calls `OnSpellStart`, waits `WaitForFirstBurstFrame` (before **every** spell; hits during the wait count), then starts `BulletManager.BurstChain(spell.Bursts, transform, onEnd)` and **polls it every fixed frame** instead of yielding on the chain (`isBurstDone` is set by `onEnd`). When `TimeLimit` runs out or HP ≤ 0 it stops the chain and moves to the next spell (a kill also starts the item drop); a chain that finishes is restarted at once while time and HP remain. After the last spell it sets `isDead` and calls `OnDie`. Known quirk: by the time `Run` sees a kill, `HitCheck` has already stopped the chain, so `Run` restarts it and stops it again in the same frame, and the opening bullets (and move tween) of the spell's first burst replay at the moment of the kill.
- Never `yield return` a chain coroutine you may `StopCoroutine`: a coroutine waiting on a stopped coroutine is never resumed. That is why `Run` polls.
- `Enemy.HitCheck` (in `FixedUpdate`, skipped once `isDead`) only takes damage: `enemyHP--`, `OnHit`, and at HP ≤ 0 it stops the current chain and sets `isBurstDone` — it does **not** kill; `Run` advances the spell. So a multi-spell boss plays every spell, and the enemy dies only after its last spell (killed or timed out).
- `OnDie` (only from `Run`) awards `EnemyPattern.Score` regardless of how the last spell ended (kill or timeout — scoring is a known open design point) and releases the enemy. `EnemyBoss` drives the boss UI (name; HP bar refilled per spell) and on death tweens off the top for 3 s before releasing.
- `BulletManager.BurstChain(bursts, presenter, onEnd)` invokes `onEnd` only when the chain finishes normally (not when stopped). A burst with `WaitForFrame > 0` also DOTween-moves the presenter to `PresentPosition` over that duration — **enemy movement is authored as bursts**; bursts with 0 wait only fire. Each BulletPattern spawns one bullet, then waits its own `WaitForFrame`.
- The player auto-fires `PlayerData.PlayerAttacks[power]` every 5 frames via `BulletPatternChain`, where `power` = whole part of the current power (0–5). Each player maps power 0–5 to bursts 0, 1, 1, 2, 2, 3 of its own set in `Datas/Bursts/Player/`: Baekyeon `Baekyeon_Spread`–`Spread3` (1/3/5/7-way spreads of `P_Baekyeon`), Yujin `Yujin_Straight`–`Straight3` (1 or 3 straight `P_Yujin` shots, plus `NearestEnemyTargettingSequence` homing shots from `Straight2` on). `l4`/`l5` are unused leftovers.

### Bullets

- `Bullet` is a plain C# class (not a GameObject), pooled by `BulletManager` (`ObjectPool` keeps up to 1024 released bullets; the live count is unbounded). `BulletManager.FixedUpdate` updates live bullets, releases dead / out-of-deadzone ones with in-place compaction (spawn order is preserved — render order depends on it), then calls `BulletCollision.Rebuild`. The deadzone is `BulletManager.prefab`'s `Bullet Min`/`Bullet Max` children, ±9.5 × ±10.5 — barely past the screen (±8.9 × ±10): a bullet fired from or flying outside it is released on the next fixed frame, so enemies must fire from on-screen and upward arcs must stay below 10.5.
- To destroy a bullet set `IsAlive = false`; never remove or reorder `ActiveBullets` elsewhere — the collision grid stores indices into that list until the next rebuild.
- `BulletTag` is a `[Flags]` enum: `Enemy` 1, `Player` 2, `Power` 4, `Score` 8, `Item` = `Power | Score`. The tag is the **shooter**, and `Check`/`CheckAll` take the tag of the bullets to look for. `BulletCollision` keeps one static uniform grid per tag bit: a bullet goes into the grid of every bit in its tag, a query searches the grid of every bit in the requested tag, and a `Tag = 0` bullet is never registered (it hits nothing and can't be bomb-cleared). `Check`/`CheckAll` test a circle against circle bullets and lasers (`BulletData.Distance` = radius or laser length). The player checks `Enemy` bullets (radius 0), enemies check `Player` bullets with `Body.Distance`, and a bomb clears `Enemy` bullets.
- Movement: `BulletSequenceBase` (SO) → `ISequenceRunner` (`Start` once, `Next` per frame). `DefaultSequence` (linear + torque), `AccelateSequence` (curve to target speed, then acceleration), `TargettingSequence` (aims at the player on start; initial velocity = speed + angle offset), `NearestEnemyTargettingSequence` (for player bullets: aims the same way at the nearest active `Enemy` inside `AreaMin`/`AreaMax`, optionally preferring the player's `Left`/`Right` side; straight up if there is none), `RandomDirectionSequence` (random direction at 0–|initial velocity| speed, then linear + torque), `DownwardSequence` (keeps its speed and heads straight down; meant to follow another sequence in a bridge), `GravitySequence` (constant acceleration `Gravity` with speed capped at `MaxSpeed`, so it bends toward the gravity direction — fountain/falling bullets; no torque), `StopAndAimSequence` (slows linearly to a stop over `StopFrame`, then at bullet age `AimFrame` flies at the player's current position at `AimSpeed`, or straight down without a player; no torque), `SequenceBridge` (chains sequences at frame counts, calling each child's `Start` when it takes over). Stateless runners share a static `Singleton`, settings-only runners are cached per asset, and stateful ones are created per bullet (see the authoring rules).
- `BulletRenderer` draws `ActiveBullets` with `Graphics.DrawMeshInstanced`, batched per sprite in chunks of 1023, using a runtime copy of `04.Materials/Bullet01.mat` (shader `Custom/URP/Sprite Invert Multiply`). Meshes come from sprite vertices/UVs, so the tightly packed atlas `03.Textures/AtlasSet.spriteatlasv2` renders correctly. It only reads bullet data.
- The game camera renders into `03.Textures/InGame.renderTexture`, shown in the UI (the gameplay view is not the screen directly).

### Rules for authoring danmaku data

When asked to create bullet/danmaku data:

- Change only data assets (`Assets/Datas/`) and sequence scripts. **Never modify any other script** (`Bullet`, `BulletManager`, `Enemy`, …): any new movement must be solvable entirely inside a sequence.
- A new sequence goes in `02.Scripts/Spell/Bullet/Sequence/`, inherits `BulletSequenceBase`, and keeps its `ISequenceRunner` as a **`private` nested class** inside the sequence class (as `DefaultSequence.DefaultRunner` does). Expose it only through `GetSequenceRunner()`.
- Reusable runners must be shared to save memory: a runner with no state at all is a static singleton (`private static readonly … Singleton = new();`, returned from `GetSequenceRunner()`, as in `DefaultSequence`). A runner that only reads the SO's settings (no per-bullet state) can't be a static singleton since each asset has its own values — cache one per asset (a lazily created `[System.NonSerialized]` field on the sequence) and return that. Only runners holding per-bullet state (start frame, child runners, …) are created per call, as `AccelateSequence`/`SequenceBridge` do. Per-bullet data lives in `Bullet` (`Position`, `Velocity`, `Torque`, `Elapse`, `bulletColor`), never in a shared runner.
- Every SpellCard's burst chain needs at least one wait (some `BurstData.WaitForFrame` or `BulletPattern.WaitForFrame` > 0). A chain with no wait finishes inside `StartCoroutine`, so `Enemy.Run` restarts it forever within one frame and the Editor freezes (`Spells/Common/Common1` is such a spell; it's unused).
- Give every new BulletData an explicit `Tag` (`Enemy` for enemy bullets); `0` means no collision.

### Player / status / input

- `StatusManager`: HP and power are `int`s in **hundredths** (`MAX_HP = MAX_POWER = 500` = 5.00; `UpdateHP`/`UpdatePower` and the `HP`/`Power` properties pass the value ÷100 as `float`), score, high score (`DataSaveLoad` → PlayerPrefs, only ever raised), exposed as `UnityEvent`s with C# `event` wrappers. `Hit()` fires `OnPlayerHit` at once (the player stops moving/firing and turns invincible). 18 frames later, unless `TryUsePower` (bomb, −100) / `TryUseSemiPower` (−50) cancelled it, HP drops by 100 and `OnPlayerDie` respawns the player at (0, −7) with 300 invincible frames — or, once HP goes **below 0** (0 is the last life), it's game over: save high score, pause, result panel, `OnGameOver`. `Initialize(hp, power)` (called from `PlayerController.Initialize`) only stores the values; `StatusManager.Start` applies them and pushes the initial UI values.
- Online leaderboard (not wired into the game): `DataSaveLoad.PostScores`/`GetScores` POST/GET `{name, score}` JSON at `<URL>/score`, retrying on connection errors, 429 and 5xx. The URL is read from `Resources/apiurl.txt`, which is gitignored (it holds the server address) and not supplied by CI. `Core/DatabaseAPI` wraps them but isn't placed anywhere; only `Test/DBTest` (scene `AWSTest`) calls `GetScores`. `Newtonsoft.Json` is only a transitive package dependency (`com.unity.nuget.newtonsoft-json` isn't in `manifest.json`).
- `PlayerController` is built in code (`Initialize(PlayerData)`) and clamps movement to the scene object `Deadzone`'s `Min`/`Max` children (found with `GameObject.Find("Deadzone")` in `Start`); a bomb calls `BulletManager.BulletClearing` (expanding clear radius) and grants 300 invincible frames, a semi-bomb only the invincibility. `PlayerAnimation` sets the Animator int param `Right` (-1/0/1), fades the sprite on `PlayerController.OnInvisibility`, and on `OnPlayerHit` squashes and fades the player out (reversed on `OnPlayerDie`; any power change, e.g. a bomb, resets the squash).
- Input: the `PlayerInput` in `Resources/ManagerObjects/Input Handler.prefab` (*Invoke Unity Events*; actions in `Assets/Settings/InputSystem_Actions.inputactions`) binds Move → `InvokeOnMove`, LowSpeed → `ChangeSlowMoveState`, and Bomb → the parameterless `InvokeOnUseBomb()` (so it fires on press *and* release); the on-screen "Low Speed Modifier" `HoldButton` in `UIManager.prefab` → `ChangeSlowMoveState(bool)`. Bindings resolve by method name and parameter type — renaming or removing an overload breaks them silently. Gameplay subscribes to `OnMove`/`OnUseBomb`/`OnUseSemiBomb` and reads `IsSlowMoving`.

### Editor tools (`02.Scripts/Editor/`)

`BulletDataEditor` / `BurstDataEditor` (sprite, hitbox and burst previews), `DeadzoneGizmos` (scene-view rects for the bullet deadzone; its player rect still reads the removed `<DeadzoneMinTr>k__BackingField`, so it draws nothing), and play-mode test inspectors `StageRunEditor` ("시작"; the only way to start InGame's scene `StageRunner`), `StatusManagerEditor`, `UIManagerEditor`. `BurstDataEditor` simulates with the real `Bullet`/sequence code but hardcodes InGame's layout (screen ±8.9 × ±10, bullet deadzone ±15 — wider than the game's ±9.5 × ±10.5, see Bullets — player start (0, −7)) and never moves the presenter — update it if the scene layout changes. It previews one burst from an editable fire position (default (0, 5)), where aim sequences can't aim: unless the open scene has a `PlayerController`, `TargettingSequence` logs an error and keeps the raw velocity, and with no enemy in the scene `NearestEnemyTargettingSequence` treats straight up as the target.
