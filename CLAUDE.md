# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Danmaku (탄막 게임) — a 2D bullet-hell game built with **Unity 6000.3.23f1**, URP 2D renderer, the new Input System, and DOTween. Commit messages, code comments and docs are in Korean. `.editorconfig`: UTF-8, LF.

`CODEBASE_GUIDE.md` (Korean, per-class reference) is generated by Copilot via `.github/workflows/docs.yml` (push a `docs` tag) from whatever commit was tagged, so it can lag behind the code (its prompt still describes a removed `EnemyData` layer) — trust the source over it, and don't hand-edit it.

## Build / Run

- Running anything needs the Unity Editor (matching version). There are no lint or test commands and no tests (Unity Test Framework is installed but unused).
- Compile check without the Editor: `dotnet build Danmaku.slnx` (builds `Assembly-CSharp`, `Assembly-CSharp-Editor` and the `-firstpass` plugin projects). The `.slnx`/`.csproj` files are generated by the Editor, gitignored, point at the local Editor install and list every script explicitly — a newly added `.cs` file isn't compiled until Unity regenerates them.
- Build Settings scenes (all in `Assets/01.Scenes/Online/`): `Title`, `LevelSelect`, `Settings`, `InGame`, `SummitScore`, `Tutorial`. Title's buttons use `UI/LoadSceneAdditiveProxy` / `UI/LoadSceneProxy` (a `sceneName` field, wired to `GameManager.Instance` in `Start`): Start → `LevelSelect` and Option → `Settings`, both loaded **additively** over Title (they unload themselves on return), Tutorial → `Tutorial` (single load, see Tutorial). `LevelSelector.Confirm` calls `GameManager.LoadInGameScene(level, player)`, which loads InGame and creates the "Runner" (`LevelRunner`) and, through `GameManager.SpawnPlayer`, the "Player" (`PlayerController` + `PlayerAnimation`) at runtime. Test-only scenes are in `01.Scenes/Test/`.
- InGame has **no player and no runner**: opening it directly in Play mode gives an empty field. Play through Title → LevelSelect, or open `Tutorial`, which spawns its own player. Each level holds two stages, `E1_Stage` and `E2_Stage` (one phase each: about a minute of fairies, then a last boss with three spells): `Datas/Levels/Esay` uses `Stages/EasyCopy/`, `Normal` uses `Stages/Easy/` and `Hard` uses `Stages/HardCopy/` (the `Copy` folders are per-difficulty copies; bursts and spells sit in the same-named folders under `Bursts/` and `Spells/`, split into `Common`, `Stage1` and `Stage2`). The older `Stage1` (phase 1: only a mid-boss; phase 2: six fairies, then the last boss) is in no level. Keys: move WASD/arrows, slow Shift/Space/L, bomb X/K; the player auto-fires.
- Enter Play Mode Options has **domain reload disabled** (`ProjectSettings/EditorSettings.asset`), so static fields and static event subscriptions survive between play sessions — reset new static state explicitly (e.g. `[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]`).
- CI (`.github/workflows/build.yml`) builds **WebGL** (also the Editor's active platform) with `game-ci/unity-builder` when a `v*` tag is pushed (or on manual dispatch); the bot commits the output into `docs/` (GitHub Pages) with `[skip ci]`. Never hand-edit `docs/`.
- **DOTween Pro is a paid asset and is gitignored** (`Assets/Plugins/Demigiant/DOTweenPro*`, `DemiLib`; only free DOTween is tracked). It must exist locally: scenes use its `DOTweenAnimation`/`DOTweenVisualManager` components (Title, LevelSelect, SummitScore, the InGame UI, `HitPoint`, the background), and `UIManager` and `ScoreSummit` reference `DOTweenAnimation` in code, so **without it the scripts don't compile** (defines `DOTWEEN;DOTWEENPRO` are set). CI copies it from the private `PrivateStorage` repo. Never commit it.

## Architecture

Scripts live in `Assets/02.Scripts/`, compiled into `Assembly-CSharp` (no asmdefs; `Editor/` goes to `Assembly-CSharp-Editor`, `Assets/Plugins/` to the `-firstpass` assemblies). Asset folders are number-prefixed (`01.Scenes`, `02.Scripts`, `03.Textures`, `04.Materials`, `05.Prefabs`).

### Managers / singletons

- `Core/SingletonBehaviour<T>`: `Instance` finds an active `T` in the scene, and if there is none it **instantiates the first `T` prefab in `Resources/ManagerObjects/`** (with a warning). Use `ExistingInstance` in teardown code (`OnDisable`/`OnDestroy`) to avoid spawning one. Duplicates `Destroy` themselves in `Awake`, but the destroy is deferred, so subclasses overriding `Awake` must call `base.Awake()` and guard their own setup with `ExistingInstance == this`. `IsPersistent` enables `DontDestroyOnLoad` (`GameManager`, placed in Title, InGame and Tutorial; `AudioManager`, placed only in Title, so playing InGame or Tutorial directly spawns it from `Resources` with that warning). A scene-placed instance counts as usable before its own `Awake` (`IsUsable` checks `enabled` + `activeInHierarchy`, not `isActiveAndEnabled`).
- InGame holds prefab instances of `UIManager` (which nests `Input Handler.prefab` — `InGameInputHandler` + `PlayerInput` — and `StatusManager`), `GameManager`, `EnemyManager` and `BulletManager`, plus scene objects (`Game Camera`, `UI Camera`, `EventSystem`, `Deadzone`, `BulletRenderer`, `HitPoint`, the `Forest` background). There is no `StageRunner` in the scene.
- A UnityEvent serialized in a prefab can only target objects inside that prefab or other assets, so pointing it at another manager calls the **prefab asset**, not the live singleton. Wire cross-manager calls in code through `.Instance` (as `UI/LoadSceneProxy` does). `Resources/ManagerObjects/StatusManager.prefab`'s events have no target; the instance nested in `UIManager.prefab` overrides them to the `UIManager` setters, and `UIManager.Awake` also subscribes those setters in code, so each status update is applied twice — harmless.
- UIManager panels: the result panel (a DOTween Pro `DOTweenAnimation` with id `RESULT`, played forward by `ResultBoardOn` and rewound when `UIManager` initializes) has a Continue button whose `UI/LevelContinueFinder` adds `LevelRunner.StartLevel` in `Start` — it throws in a scene without a `LevelRunner`, which is why Tutorial disables the panel. The retry panel (opened by `ScoreSummit` after a game over) has 계속 하기 → `StatusManager.Retry` and 타이틀로 → `LoadSceneProxy` (Title).

### Timing

All gameplay runs in `FixedUpdate` (Fixed Timestep = 1/60) and moves with `Time.fixedDeltaTime`. Durations in data and code are **fixed frames**: wait with `yield return new WaitForFixedFrame(n)` (`Core/`) or the cached `GameManager.WaitForFixedUpdate`; `GameManager.FrameToSecond`/`SecondToFrame` convert for DOTween. `GameManager.Pause()`/`Resume()` are ref-counted and set `Time.timeScale` (0 halts `FixedUpdate`, i.e. all gameplay); `LoadScene` and every scene load reset them.

### Danmaku data (ScriptableObjects in `Assets/Datas/`, menus under Level/Stage/Spell/Bullet/Player)

```
LevelData (Datas/Levels: Esay/Normal/Hard, two stages each) → StageData[]
StageData → PhaseData[] → EnemyChain[] → EnemyPattern[]   (+ PhaseData.Boss: EnemyPattern, spawned after the chains)
  EnemyPattern (struct: type, name, color, score, Body: BulletData, AniCon, SpellCard[], spawn pos, item drop counts, first-burst wait)
    SpellCard (PresentHP, TimeLimit) → BurstData[] (PresentPosition, WaitForFrame) → BulletPattern[]
      BulletPattern = BulletData + InitialBullet (color/pos/vel/torque) + BulletSequenceBase + WaitForFrame
```

`PlayerData` (`Datas/Players`: Baekyeon, Yujin): Speed, SlowSpeed, InitialHP/InitialPower (hundredths, 0–500), `PlayerAttacks: BurstData[]` (indexed by power level 0–5, so it needs 6 entries), `PlayerSpell` (the bomb: a SpellCard in `Datas/Spells/Player/`, `Baekyeon_Bomb`/`Yujin_Bomb`, whose bursts `PlayerController` fires once per bomb), `AniCon`. `LevelData.ScoreMultiplyer` is a `double` (Esay 1, Normal 3.4, Hard 10.3); `StatusManager.CalculateResultScore` multiplies the result bonus (HP, power, stage) by it, and the result panel shows `<level name> Rank`, the multiplier and the total.

`SpellCard.TimeLimit` is an `int` in frames, counted from that spell's start (after its wait): `N > 0` repeats the burst chain until N frames pass, while `0` **or any negative value** ends the spell at its first check, so only the chain's bullets before its first wait fire (a one-spell enemy then dies and scores right away). There is no "never" value: for a spell that should last until the enemy is killed, use a huge limit (e.g. `2147483647`). A regular enemy's limit should end when its MoveOut burst has taken it off-screen, otherwise the repeated chain brings it back in. Most existing spells (31 of 35) still have `0`, and every `Bursts/Stage1/*` burst has `PresentPosition = (0, 0)` with `WaitForFrame > 0`, so Stage1 enemies fly to the screen centre — both are data still to be fixed.

Every enemy BulletData has `Tag = Enemy` except the unused `BulletDatas/Laser`, saved before `BulletData.Tag` existed (`Tag` `0` = no collision, see Bullets).

Items are BulletData tagged `Power`/`Score` (`Datas/Items`; sprites in `03.Textures/Items/`). When a spell is **killed** (not timed out), `Enemy.ItemFirework` drops `EnemyPattern.DropPowerCount` power items and `DropScoreCount` score items, all in the same frame at the enemy's position, through `BulletManager.SpawnPowerItem`/`SpawnScoreItem` (the `Stages/Easy` fairies drop 2–3 power and 1–2 score, bosses far more). Those spawn the `PowerItemPattern`/`ScoreItemPattern` set on `BulletManager.prefab`, whose sequence `Sequences/RandomThenDown_18F` runs `RandomDirectionSequence` for 18 frames, then `DownwardSequence`. Both runners **ignore the initial velocity** (see Bullets), so they are effectively item-only. `PlayerController.InhaleItem` runs every fixed frame while alive: it pulls `Item` bullets within 3 units toward the player at 20 units/s and collects them once close (power item +1 power (hundredths) and +100 score, score item +1000 score); while the player is down, pulled items fall again at 2 units/s. When a boss starts a spell or dies, `BulletManager.RemoveAllBullets` turns every live `Enemy` bullet into a score item.

There is no separate enemy asset: enemies are defined inline in `EnemyPattern` inside `PhaseData`. An enemy's hit radius comes from its `Body` BulletData (`Distance`), and its sprite from `Body.BulletImage` unless `EnemyPattern.AniCon` is set: `EnemyManager.SpawnEnemy` assigns it to the prefab's Animator (null = no animation), and the clips then drive the sprite (without one, both prefabs show a plain white square). Only the `Stages/Easy` phases set it (`Animate/Enemy/Fairy/Fairy.controller` for fairies, `Boss/Boss.controller` for bosses).

Most data fields are `[field: SerializeField]` auto-properties, serialized as `<Name>k__BackingField` (`BulletDataEditor` and `DeadzoneGizmos` look them up by that string). Renaming such a property drops its saved values unless you add `FormerlySerializedAs("<OldName>k__BackingField")`.

### Runtime flow

- Level flow: `LevelRunner.Initialize(level)` sets a stage enumerator; `Start` creates its own "Runner" `StageRunner` and calls `StartLevel` (resume, next stage → `Initialize` + `StartRun`). Each stage end pauses on the result panel, whose Continue button calls `StartLevel` again; after the last stage it loads `SummitScore` additively (see Player / status).
- `StageRunner` walks phases as a coroutine: it spawns each chain's patterns via `EnemyManager.SpawnEnemy` (pooled `05.Prefabs/EnemyPrefab` for `EnemyType.Common`, 10 pre-warmed in `EnemyManager.Start`; otherwise instantiates `BossPrefab` / `EnemyBoss`) without waiting for them to die, then, if `PhaseData.Boss.Type` isn't `Common`, spawns the boss and waits on `EnemyBoss.BossAlive()`. 300 frames after the last phase it pauses, adds the result bonus (`StatusManager.CalculateResultScore(StageID)`) and shows the result panel (`UIManager.ResultBoardOn`).
- `Enemy.StartPattern` runs each SpellCard in its `Run` coroutine: sets HP to `PresentHP` and calls `OnSpellStart`, waits `WaitForFirstBurstFrame` (before **every** spell; hits during the wait count), then starts `BulletManager.BurstChain(spell.Bursts, transform, onEnd)` and **polls it every fixed frame** instead of yielding on the chain (`isBurstDone` is set by `onEnd`). It raises the protected events `RemainingSpellCount` (at each spell start) and `RemainingTime` (seconds left, every polled frame), which `EnemyBoss` routes to the boss UI. When `TimeLimit` runs out or HP ≤ 0 it stops the chain and moves to the next spell (a kill also drops items); a chain that finishes is restarted at once while time and HP remain. After the last spell it sets `isDead` and calls `OnDie`. Known quirk: by the time `Run` sees a kill, `HitCheck` has already stopped the chain, so `Run` restarts it and stops it again in the same frame, and the opening bullets (and move tween) of the spell's first burst replay at the moment of the kill.
- Never `yield return` a chain coroutine you may `StopCoroutine`: a coroutine waiting on a stopped coroutine is never resumed. That is why `Run` polls.
- `Enemy.HitCheck` (in `FixedUpdate`, skipped once `isDead`) only takes damage: every `Player` bullet inside the radius (`CheckAll`) hits in the same frame (`enemyHP -= bullet.Damage`, `OnHit`, +`Score / 10`), and at HP ≤ 0 it stops the current chain, sets `isBurstDone` and checks no further bullets — it does **not** kill; `Run` advances the spell. So a multi-spell boss plays every spell, and the enemy dies only after its last spell (killed or timed out).
- `OnDie` (only from `Run`) awards `EnemyPattern.Score` regardless of how the last spell ended (kill or timeout — scoring is a known open design point) and releases the enemy. `EnemyBoss` drives the boss UI (name; HP bar refilled per spell; remaining spell count and time) and on death tweens off the top for 3 s before releasing. A released or destroyed enemy kills its DOTweens (`DOTween.Kill(transform)`).
- `BulletManager.BurstChain(bursts, presenter, onEnd)` invokes `onEnd` only when the chain finishes normally (not when stopped). A burst with `WaitForFrame > 0` also DOTween-moves the presenter to `PresentPosition` over that duration — **enemy movement is authored as bursts**; bursts with 0 wait only fire. Each BulletPattern spawns one bullet, then waits its own `WaitForFrame`.
- The player auto-fires `PlayerData.PlayerAttacks[power]` every 5 frames via `BulletPatternChain`, where `power` = whole part of the current power (0–5). Each player has six bursts in `Datas/Bursts/Player/`, one per power level: Baekyeon `Baekyeon_Spread`, `Spread1`, `Spread1_Power2`, `Spread2`, `Spread2_Power4`, `Spread3` (spreads of `P_Baekyeon`), Yujin `Yujin_Straight`, `Straight1`, `Straight1_Power2`, `Straight2`, `Straight2_Power4`, `Straight3` (straight `P_Yujin` shots, plus `HomingSequence` shots via `Sequences/PlayerHomingLeft`/`Right` from `Straight2` on). `<Name>_Bomb` are the bombs' bursts (Yujin's uses `RandomAreaSpawnSequence`). `l4`/`l5` are unused leftovers.

### Bullets

- `Bullet` is a plain C# class (not a GameObject), pooled by `BulletManager` (`ObjectPool` keeps up to 4096 released bullets and is pre-warmed with 1024 in `Start`; the live count is unbounded). `BulletManager.FixedUpdate` updates live bullets, releases dead / out-of-deadzone ones with in-place compaction (spawn order is preserved — render order depends on it), then calls `BulletCollision.Rebuild`. The deadzone is `BulletManager.prefab`'s `Bullet Min`/`Bullet Max` children, ±9.5 × ±10.5 — barely past the screen (±8.9 × ±10): a bullet fired from or flying outside it is released on the next fixed frame, so enemies must fire from on-screen and upward arcs must stay below 10.5.
- To destroy a bullet set `IsAlive = false`; never remove or reorder `ActiveBullets` elsewhere — the collision grid stores indices into that list until the next rebuild.
- `BulletTag` is a `[Flags]` enum: `Enemy` 1, `Player` 2, `Power` 4, `Score` 8, `Item` = `Power | Score`. The tag is the **shooter**, and `Check`/`CheckAll` take the tag of the bullets to look for. `BulletCollision` keeps one static uniform grid per tag bit: a bullet goes into the grid of every bit in its tag, a query searches the grid of every bit in the requested tag, and a `Tag = 0` bullet is never registered (it hits nothing and can't be bomb-cleared). `Check`/`CheckAll` test a circle against circle bullets and lasers (`BulletData.Distance` = radius or laser length). The player checks `Enemy` bullets (radius 0), enemies check `Player` bullets with `Body.Distance`, and a bomb clears `Enemy` bullets.
- Movement: `BulletSequenceBase` (SO) → `ISequenceRunner` (`Start` once, `Next` per frame). `DefaultSequence` (linear + torque), `AccelateSequence` (curve to target speed, then acceleration), `TargettingSequence` (aims at the player on start; initial velocity = speed + angle offset), `NearestEnemyTargettingSequence` (for player bullets: aims the same way at the nearest active `Enemy` inside `AreaMin`/`AreaMax`, optionally preferring the player's `Left`/`Right` side; straight up if there is none), `RandomDirectionSequence` (random direction at a speed of 0–4, ignoring the initial velocity, then linear + torque), `DownwardSequence` (heads straight down at 2 units/s whatever its speed; meant to follow another sequence in a bridge), `GravitySequence` (constant acceleration `Gravity` with speed capped at `MaxSpeed`, so it bends toward the gravity direction — fountain/falling bullets; no torque), `StopAndAimSequence` (slows linearly to a stop over `StopFrame`, then at bullet age `AimFrame` flies at the player's current position at `AimSpeed`, or straight down without a player; no torque), `HomingSequence` (player bullets: turns toward the nearest enemy at up to `TurnRate` deg/s, proportional to the angle gap via `TurnGain`, with the cap rising by `TurnAcceleration` so it can't orbit; optional `Left`/`Right` side preference; re-targets when the target is released, flies straight with no enemy; no torque), `RandomAreaSpawnSequence` (moves the bullet to a random world point in `AreaMin`/`AreaMax`, holds `HoldFrame` frames, then accelerates along the initial velocity direction with a random torque within ±`TorqueRange`; can track the nearest enemy; ignores the presenter, `InitialPosition` and initial torque; used for Yujin's bomb), `SequenceBridge` (chains sequences at frame counts, calling each child's `Start` when it takes over). Stateless runners share a static `Singleton`, settings-only runners are cached per asset, and stateful ones are created per bullet (see the authoring rules).
- `BulletRenderer` draws `ActiveBullets` with `Graphics.DrawMeshInstanced`, batched per sprite in chunks of 1023, using a runtime copy of `04.Materials/Bullet01.mat` (shader `Custom/URP/Sprite Invert Multiply`). Meshes come from sprite vertices/UVs, so the tightly packed atlas `03.Textures/AtlasSet.spriteatlasv2` renders correctly. It only reads bullet data. It fills `unity_SpriteRendererColorArray` with white, since the shader multiplies by the SpriteRenderer color, which `DrawMeshInstanced` doesn't supply.
- The game camera renders into `03.Textures/InGame.renderTexture`, shown in the UI (the gameplay view is not the screen directly).

### Rules for authoring danmaku data

When asked to create bullet/danmaku data:

- Change only data assets (`Assets/Datas/`) and sequence scripts. **Never modify any other script** (`Bullet`, `BulletManager`, `Enemy`, …): any new movement must be solvable entirely inside a sequence.
- A new sequence goes in `02.Scripts/Spell/Bullet/Sequence/`, inherits `BulletSequenceBase`, and keeps its `ISequenceRunner` as a **`private` nested class** inside the sequence class (as `DefaultSequence.DefaultRunner` does). Expose it only through `GetSequenceRunner()`.
- Reusable runners must be shared to save memory: a runner with no state at all is a static singleton (`private static readonly … Singleton = new();`, returned from `GetSequenceRunner()`, as in `DefaultSequence`). A runner that only reads the SO's settings (no per-bullet state) can't be a static singleton since each asset has its own values — cache one per asset (a lazily created `[System.NonSerialized]` field on the sequence) and return that. Only runners holding per-bullet state (start frame, child runners, …) are created per call, as `AccelateSequence`/`SequenceBridge` do. Per-bullet data lives in `Bullet` (`Position`, `Velocity`, `Torque`, `Elapse`, `bulletColor`), never in a shared runner.
- Every SpellCard's burst chain needs at least one wait (some `BurstData.WaitForFrame` or `BulletPattern.WaitForFrame` > 0). A chain with no wait finishes inside `StartCoroutine`, so `Enemy.Run` restarts it forever within one frame and the Editor freezes (`Spells/Common/Common1` is such a spell; it's unused).
- Give every new BulletData an explicit `Tag` (`Enemy` for enemy bullets); `0` means no collision.

### Player / status / input

- `StatusManager`: HP and power are `int`s in **hundredths** (`MAX_HP = MAX_POWER = 500` = 5.00; `UpdateHP`/`UpdatePower` and the `HP`/`Power` properties pass the value ÷100 as `float`), score, high score (`DataSaveLoad` → PlayerPrefs, only ever raised), exposed as `UnityEvent`s with C# `event` wrappers. `Hit()` fires `OnPlayerHit` at once (the player stops moving/firing and turns invincible). 18 frames later, unless `TryUsePower` (bomb, −100) / `TryUseSemiPower` (−50) cancelled it, HP drops by 100 and `OnPlayerDie` respawns the player at (0, −7) with 300 invincible frames — or, once HP goes **below 0** (0 is the last life), it's game over: save high score, pause, load `SummitScore` additively, `OnGameOver`. `Retry()` re-applies the initial values, resumes and puts the player back at (0, −7). `Initialize(hp, power, multiplier, levelName)` (called from `PlayerController.Initialize` with the `LevelRunner`'s level, or multiplier 1 and an empty name when there is none) only stores the values; `StatusManager.Start` applies them and pushes the initial UI values, so the player must be created before any `Start` runs.
- Score submission: game over and level clear load `SummitScore` additively. Its `Core/ScoreSummit` shows `StatusManager.TotalScore` and the top 10 from `DataSaveLoad.GetScores`, and submits a nickname with `PostScores` (GET/POST `{name, score}` JSON at `<URL>/score`, retrying on connection errors, 429 and 5xx). Its return button opens the InGame retry panel after a game over (`IsPlayerDie`) and loads Title after a clear. The URL is read from `Resources/apiurl.txt`, which is gitignored (it holds the server address) and not supplied by CI; `DataSaveLoad` doesn't null-check it. `Core/DatabaseAPI` and `Test/DBTest` (scene `Test/AWSTest`) are test leftovers. `Newtonsoft.Json` is only a transitive package dependency (`com.unity.nuget.newtonsoft-json` isn't in `manifest.json`).
- `PlayerController` is built in code (`GameManager.SpawnPlayer(PlayerData)` → `Initialize`, start position (0, −7)) and clamps movement to the scene object `Deadzone`'s `Min`/`Max` children (found with `GameObject.Find("Deadzone")` in `Start`); a bomb calls `BulletManager.BulletClearing` (expanding clear radius), fires `PlayerData.PlayerSpell.Bursts` and grants 300 invincible frames, a semi-bomb only the invincibility. `PlayerAnimation` sets the Animator int param `Right` (-1/0/1), fades the sprite on `PlayerController.OnInvisibility`, and on `OnPlayerHit` squashes and fades the player out (reversed on `OnPlayerDie`; any power change, e.g. a bomb, resets the squash).
- Audio: `AudioManager` (`Resources/ManagerObjects/AudioManager.prefab`, mixer `Assets/Audio/Master.mixer`, clips in `Audio/sfx/`) maps the global `Kind` enum (in `AudioManager.cs`) to clips through its `sfxClips` list; `PlayOneShotSFX(Kind)` plays each kind at most once per fixed frame. Enemy shots (`Enemy`-tagged patterns in `BulletManager.SpawnBulletChain`), player shots, enemy hits and deaths, item pickup, player hit and bomb play SFX; `PowerUp`, `Enter` and `Exit` have clips but no caller yet. No BGM is played.
- Input: the `PlayerInput` in `Resources/ManagerObjects/Input Handler.prefab` (*Invoke Unity Events*; actions in `Assets/Settings/InputSystem_Actions.inputactions`) binds Move → `InvokeOnMove`, LowSpeed → `ChangeSlowMoveState(CallbackContext)` and Bomb → `InvokeOnUseBomb(CallbackContext)` (press only). `UIManager.prefab`'s Input Area holds the on-screen controls in left- and right-hand variants: a stick or D-pad (`OnScreenStick`; the D-pad base is also a `HoldButton`), "Low Speed Modifier" (`Button` + `HoldButton` → `ChangeSlowMoveState(bool)`, labelled Slow) and "Bomb Button" (`TapButton` → parameterless `InvokeOnUseBomb()`, labelled Bomb; its `Button` is only interactable at power ≥ 1). `UIManager.Start` turns on the variant chosen in `Settings` (stick/D-pad, hand, which button is on top; `HUDPos` is unused), edited in the Settings scene (`Core/SettingPanel` → `GameManager.ApplySettings`, saved to PlayerPrefs). Bindings resolve by method name and parameter type — renaming or removing an overload breaks them silently. Gameplay subscribes to `OnMove`/`OnUseBomb`/`OnUseSemiBomb` and reads `IsSlowMoving`.

### Tutorial

- `Online/Tutorial.unity` is a **copy of InGame** (changes to InGame's scene objects don't carry over — copy them by hand; prefab changes do) with the result panel disabled as a prefab override, plus a "Tutorial" object: `Tutorial/TutorialRunner`, a "Bomb Step Presenter" at (0, 0) and its own overlay Canvas (sort order 1, `CanvasScaler` copied from the UIManager canvas) with the guide panel over the top of the game view (step/description text, progress bar, Exit button = `LoadSceneProxy` → Title, labelled 건너뛰기, then 타이틀로 when done).
- `TutorialRunner.Awake` spawns the player with `GameManager.SpawnPlayer(playerData)` (Baekyeon). Steps, in fixed frames: intro (90) → move (`moveFrame` = 120 frames in which the player actually moved) → slow (`slowFrame` = 120 moving frames with `IsSlowMoving`) → bomb → done; each finished step holds a full progress bar for 60 frames. Each step pulses (scale) the matching on-screen control, found by component among the active ones (`OnScreenStick`'s parent, the `HoldButton` that has a `Button`, the `TapButton`), so it follows the Settings layout. The texts are code constants and name the button labels (Slow/Bomb) and the keyboard keys.
- Bomb step: fills power to at least 1.00, puts the player back at (0, −7), fires `Datas/Bursts/Tutorial/Tutorial_Curtain` once (36 bullets that stop in rings of radius 1.2/2.2/3.2 around the presenter, using `Sequences/StopHold_40F`: a `StopAndAimSequence` whose `AimFrame` is `2147483647`, so they hover) and waits for `StatusManager.OnUseBomb`. Keep its bullets away from the player: after a hit, the 300-frame respawn invincibility also blocks bombs (`PlayerController.bombCooldown`), so the bomb prompt would seem broken. `OnPlayerDie` gives the lost 100 HP back before the game-over check, so the tutorial never ends in game over.

### Editor tools (`02.Scripts/Editor/`)

`BulletDataEditor` / `BurstDataEditor` (sprite, hitbox and burst previews), `DeadzoneGizmos` (scene-view rects for the bullet deadzone; its player rect still reads the removed `<DeadzoneMinTr>k__BackingField`, so it draws nothing), and play-mode test inspectors `StageRunEditor` ("시작" runs the selected `StageRunner`), `EnemyEditor` (kill the current spell, all spells, or every enemy), `StatusManagerEditor` (HP/power, hit, bomb, game over), `UIManagerEditor`. `BurstDataEditor` simulates with the real `Bullet`/sequence code but hardcodes InGame's layout (screen ±8.9 × ±10, bullet deadzone ±15 — wider than the game's ±9.5 × ±10.5, see Bullets — player start (0, −7)) and never moves the presenter — update it if the scene layout changes. It previews one burst from an editable fire position (default (0, 5)), where aim sequences can't aim: unless the open scene has a `PlayerController`, `TargettingSequence` logs an error and keeps the raw velocity, and with no enemy in the scene `NearestEnemyTargettingSequence` treats straight up as the target.

### Not implemented yet

`StageData.BGM`/`StageTitle`, `Settings.HUDPos`, any semi-bomb input (no action or button), swipe (`InGameSwipe` isn't placed anywhere and nothing subscribes to `OnSwipe`), listeners for `EnemyManager.OnRaiseBoss`, enemy animations in the older stage data (only the `Stages/Easy` phases set `EnemyPattern.AniCon`), `UI/BackgroundBlur` (unused, and its `Custom/UI/Background Blur` shader isn't in the project), and BGM playback.

## Assets / third-party

- Player characters "Baekyeon" (백연) and "Yujin" (유진): in-game sprites in `03.Textures/Mobs/Playable/<Name>/` (the full-body `<Name>.png` there is LevelSelect's character art, packed in `Mobs/Playable/Fullbody.spriteatlasv2`), clips and Animator Controllers in `Assets/Animate/Player/Baekyoun/` (spelled *Baekyoun*) and `Assets/Animate/Player/Yujin/`.
- Enemies: fairy and boss sprites in `03.Textures/Mobs/Enemy/{Fairy,Boss}/`, controllers in `Assets/Animate/Enemy/{Fairy,Boss}/`, with the same int param `Right`, which `EnemyAnimation` sets from the enemy's x movement every fixed frame. `EnemyPrefab`/`BossPrefab` render with `04.Materials/Enemy.mat` (shader `Custom/AchromaticOnlyTint`, in `03.Textures/Shaders/`): `SpriteRenderer.color` (= `EnemyPattern.EnemyColor`) tints only pixels whose R = G = B, so grey parts take the enemy's color and colored parts keep theirs.
- Runtime scripts must not use the `UnityEditor` namespace (it doesn't exist in player builds, so the WebGL CI build fails to compile); editor-only code goes in `02.Scripts/Editor/`.
- UI text uses the TMP font asset `Plugins/Suhgung-ttf/SuhgungMono12.asset` (also the TMP default), a **static** atlas (ASCII, all Hangul syllables and jamo, U+2008–U+26AC) with no fallback anywhere — any other character (e.g. `·`, `×`, kana) renders as a missing glyph until the atlas is regenerated.
- Third-party assets live in `Assets/Plugins/` (Suhgung font OFL 1.1, TextMesh Pro, DOTween). The project is MIT; add new third-party assets to the README's Third-Party table.
